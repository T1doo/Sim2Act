# 成功成果到 P-B 应用的连续入口

基线 `4855d5250fd576bb04f81faad22ca6a4ccdfcbdd`，普通开发分支 `dev/natural-pb-reuse-guide-20261016`。本轮复读 F2 主方案及既有自然 P-B 提取合同；成功成果上的提取、精确审阅、原 key 回读、内部版本和逐次运行已存在，缺口是新目标材料准备及后续步骤的可见衔接。

1. 从 P-A 的成功规范成果点击原“从此成功任务提取应用（P-B）”。原控制器核对同主体、项目、Run、Release、结果版本及完整来源证明后，显示 P-B 步骤卡。
2. 可选择已保存的不同 Goal，或在提取面板点击“准备自己的新材料与 Goal”。复用原 TXT/MD 与 Goal 保存表单，分别明确保存。返回前重新 GET 核对原成功来源、新 Goal 版本指纹和本次材料绑定；返回不提取、不运行，并清除旧审阅和确认。
3. 原审阅控制器展示来源、编辑图、新材料、完整 Goal、预算和最小权限。用户另行确认才提取；实际保存未知时保留原冻结意图，仅原 key GET 回读。核对成功后禁用重复确认，编辑才产生另一份需重新审阅的意图。本页内存保留不等于冷页自动发现未知请求。
4. 明确打开已核对草案，重新核对 candidate 与来源绑定，完整读回内部历史后才交接给原版本控制器。权限拒绝、版本冲突或内部读取失败结束本次向导，并提示已保存草案保留、从目录重选核权。迟到失败不得清除后来选择。
5. 内部版本须单独预览、勾选确认、保存，再明确创建独立实例；向导随后提供返回统一目录入口。均不自动运行或发布。
6. 从目录选择该 P-B 应用和实例，准备另一份材料及 Goal，通过既有 per-use 精确预览与明确确认建立新 Run。确认前新 GET 检查既有受限离线配置，等待期间发生其他同实例意图时停止本次提交。原 key 恢复仍只读取，实际 Worker 的配置、权限、预算、版本与 MockTransport 检查不变。

不新增 executor、后端协议、授权种类、模型批准或来源退休许可。提取仍依赖原成功来源的当前权限；旧来源撤权时保守拒绝。原应用、Goal、Release、实例及成果保持。语义 UNKNOWN、人工 PENDING、未发布分别保留，不把引用/结构检查当成真实语义验收。

本轮验收使用合成数据、实际 TestClient HTTP、生产页面脚本和 JSDOM、真实 Worker 加 httpx.MockTransport。实际结果、失败轮次、源码冻结与独审范围以同轮证据为准；不重做旧恢复矩阵，不宣称原生浏览器、Windows、PG、远端 CI、真实模型或真实场景通过。
