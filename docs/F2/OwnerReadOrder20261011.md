# owner 签收页读取顺序纠正

接续 `ed5cda2e341f0601879ad3f1e42ad1667022d490` 的[精确版本签收合同](OwnerVersionAcceptance.md)。父复审 P2 指出：打开实例后初始 GET 尚未返回，页面允许手动刷新；另一个本人会话追加 REVOKE 或 PREPARE 后，较新刷新先返回，但旧 ACCEPTED 初始响应仍可覆盖页面。本切片只修复读取资格与回执绑定，不增加签收对象、执行器、语义能力或发布权限。

`src/sim2act/web/owner-review.js` 为同一页面的初始、刷新、原 key 恢复和提交后读取统一分配单调读取代次。最新发起的读取才可安装状态；每次异步摘要之后还须重验读取、人工编辑、工作区、实例及身份选择资格。发起显式 POST 前使所有既有读取失效。内层校验抛错后，初始、刷新、恢复和提交后读取的外层 catch 还须核对刚发起的读取代次，初始读取还捕获完整编辑及导航 fence，避免两层 catch 间启动的新读取被旧错误覆盖。旧读取的成功、错误及摘要后处理不能覆盖较新状态或删除较新未确认请求。

安装响应前，核对版本、身份、项目、应用、实例、正式发布关闭及语义 UNKNOWN。历史限 256 条、连续序列、前项指纹链、唯一 ID/key、类型/状态关系、latest 与末项、已经显示的历史前缀必须一致；不能安装更低序列。相同序列仍允许服务端因撤权、版本变化或到期返回 STALE/EXPIRED，不能把状态排成永久高低等级。active record 和 recovered 必须精确对应历史元数据；指定 key 的 GET 即使本地没有 pending 请求也要核对 key。允许显示历史回执，但不能恢复旧 ACCEPTED 当前状态。

GET `/api/internal/instances/{iid}/owner-review` 在既有本人实例和项目授权检查后，补充 principal_id/project_id/app_id 范围元数据。空历史和受保护内容已隐藏的响应也因此能绑定所选范围。未新增读取旧受保护 payload、来源或运行的权限；提交、seal、全历史 payload 核验沿用现有后端。浏览器只重算 Strict 请求的整数/字符串 JSON 指纹，并精确核对元数据；含浮点字段的完整 payload 指纹和独立 seal 继续由后端核验，不宣称浏览器完成独立全 payload 指纹验证。

使用真实 SQLite、进程内 HTTP、正常 Worker 与离线 JSDOM，通过实际页面按钮触发初始读取和刷新，控制响应交付先后。另一个授权会话经实际 HTTP POST 追加精确停止或新预览。原 key 恢复与有效刷新仍可用，无自动 POST 重试，较新表单及人工草稿保留。错误响应丢失和故意坏范围/低序列/不一致回执明确标为受控故障，不能冒充服务端自然响应。另用同 Window realm deferred Promise 实测外层 catch 微任务窗口，四个外层错误回归与一个初始编辑再撤销回归仅为本地源码 JSDOM 受控调度；该夹具的摘要为 constant，不认领 HTTP、Worker、摘要等待时序或人工操作。真实摘要函数及其受控交付等待另以独立探针验证。

测试中人工选择仍为 SIMULATED。真实 owner 语义、真实模型、PG、Windows、原生浏览器、旧源码升级、完整 P-A/P-B、256 条历史耐久/性能及正式发布/部署均 NOT RUN；新精确SHA的远端 CI 未验证。本轮实际红绿、源码冻结、独立审查及保留记录见[新证据目录](../evidence/owner-read-order-20261011/README.md)，四个旧证据目录原字节不改。
