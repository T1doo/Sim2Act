## 核心结论

已有底座可以接受持久任务、保存授权材料、保存目标卡、校验声明式候选，并在内部 Release/Instance/AppRun/worker 路径中执行新参数、保存新结果和历史。最关键缺口位于“成功任务/新目标 → 平台实际自动生成候选”：目标入口只组装固定 CSV 模板；agent 初始候选和来源候选由离线 Python 调用者/测试夹具提供，HTTP/UI 没有创建它们的产品入口。agent 每次预检和运行还需调用者上传两条离线模型响应。故可体验现有内部工程链，不能体验原 V5 的完整自主应用生成主线。

## 优先补的最小体验主线

1. **先定义一条真实用户任务的完成契约和受支持表达边界。** 可沿现有TXT/MD来源证据链推进，但“字面定位”与“义务语义检查清单”是两个不同目标；若选择后者，需要独立语义oracle。记录授权材料/未见输入/错误输入/检查版本；不把gold传给生成器，不降低原目标。不应继续靠增加孤立固定转换器声称通用。
2. **连通“成功任务 → 自动候选”服务及UI。** 源自可核验成功Run的显式目标、资源hash、工具调用、成果和检查；生成器识别变量与稳定步骤、生成候选，并记录来源和介入。现有verified_source/provenance可复用，但应明示暂时仅支持的源类型。先将源码可审查的离线接口/预算门准备好，实跑另等授权。
3. **连通P-A同一生成服务。** 从冻结目标卡直接形成候选，不由用户手选唯一csv.sum、手供JSON或测试setup；不能以P-B成功代替P-A。
4. **把候选接到已有编译/内部预览/实例worker底座，替换运行时Replay要求。** 实际书生调用仅在获准预算和材料发送范围后开放；有限修复、用量/失败留账；新材料冷会话产生新AppRun和独立检查后的新结果，错误输入不写入业务状态。
5. **给已验收app一个可用的本地发布与实际使用界面。** 保留精确批准、权限交集和版本前置条件；让用户只输入业务参数/资料，不上传候选或响应wire。内部Release不改名当正式发布；受控预览写隔离与本地数据行为必须另验。
6. **补局部修改路径与现有UI阻塞。** 最小确定依赖、未知依赖扩验、锁定冲突分别可见可验；修正hidden project select和窄屏空白，再跑对应浏览器真实流程。上述完成后仍需原Windows/故障/独立评测证据，不能按阶段数字或PASS数量签收。
