# 为已保存的 Goal CSV App 追加材料授权

在“使用已保存的本地应用”中打开原 CSV 实例，或选择 App 的“管理此App的CSV材料授权”。打开与读取候选均不授权。用户必须明确选择同项目已有 CSV，核对 App/runtime、材料 ID/hash、READ 与 SUM、全部实例共用的作用范围和最长 24 小时，再单独勾选并提交。

这是原 CSV App 创建授权的有限业务扩展。服务端只给现有 App runtime 插入所选材料的 `resource.read`、`data.aggregate_csv` 两项 Grant；不创建主体，不修改用户或项目 runtime 的权限，不增加凭据、连接、系统权限或 executor。用户与项目 runtime 必须已经拥有两项上层权限，原 App 和来源也必须仍有效。外部项目、失效来源、材料/hash、候选或权限版本不匹配均拒绝。

Grant 本身属于 App runtime，供该 App 全部实例共用；各 Release 声明继续约束实际访问。授权不会自动替换材料、运行、保存版本或采纳。用户须明确开始新的材料修订，再读取新基线、选择 B，沿原材料草案 → 独立 CHECK → 内部 Release → 原实例 CAS 采纳 → 显式新 Run 进入结果。旧基线键保留，新周期使用新键；权限变化不豁免既有版本与权限检查。旧 A 的 Goal、Release、Run 和结果留作历史，人工验收保持每个新 Run 独立 PENDING。

命令绑定完整请求指纹、当前候选指纹、项目权限版本及精确 App/材料 Grant 集指纹。事务只新增两行 Grant 与原持久请求表的双锚回执；接受过程中上层权限失效会回滚。重复同键只读原受理组与当前有效性，不插入、续期或恢复撤回权限；新键使用陈旧权限基线拒绝。半回执或篡改回执继续保守拒绝。页面未知提交只能按原键 GET 恢复，不能自动换键或重发 POST；错误的纯查询键不会变成未知写入。

服务器只有在当前 owner/project/App 范围已确认、该命令两锚原本均不存在且事务回滚完成后，才附上完整原请求指纹和作用域绑定的 `NOT_ACCEPTED` 证明。页面逐字段核验后才解除未知写入锁；用户仍须明确重新读取范围、选择材料并勾选，才可用新键提交。HTTP 403/409 本身不作为未受理证明，已有任一锚、作用域不明和网络错误不走该退出路径。证明是该次事务的结果，不是永久禁止该键的 tombstone。

“读取当前App授权状态”只读控制元数据，不读 CSV、Goal 或 Run 正文。用户选择精确材料和当前 Grant 版本并单独确认后，可同事务撤回该 App 对该材料的 READ/SUM；原单 Grant CAS 撤回接口保留原语义。失去原材料读取权限后仍可核查和撤回。回执明确区分历史受理与当前 ACTIVE、PARTIAL、INACTIVE 或 REVOKED 状态，旧受理记录不代表当前权限。

账号、连接、项目、工作区、App 和实例选择的代次围栏阻止迟到回调安装到新视图。权限失效清除旧结果、列和冻结修订正文，原键及元数据控制入口保留。原键仅存当前页面内存，重开页面可粘贴原键只读查询；不写浏览器持久存储或保存令牌。

接口集中在 `/api/apps/{aid}/csv-material-access`：GET 读取可选材料，GET `/state` 读取控制状态，POST `/authorizations` 或 `/revocations` 显式提交，GET 对应 `/{request_key}` 读取原受理及当前状态。严格输入不允许客户端指定 runtime、主体或工具。

本轮使用合成材料、mock 和原 NeverModel Worker。实际通过范围、失败原件、源码和安装包散列见 [本轮证据](evidence/app-material-authorization-20261018/README.md)。Windows、原生浏览器、PostgreSQL、真实模型、真实语义/用户场景、人工签收和远端 CI 均不得由此推定通过。

资格范围为一个 App 追加一份 B。当前追加请求与控制列表均有 64 项上限；控制列表包含原 A，因此不能据此宣称支持 64 份新增 B。满额边界未执行；既有项目 Grant 元数据列表与逐 Grant CAS 撤回入口保留。
