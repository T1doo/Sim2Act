# 同一 CSV 应用的 Goal 修订与原实例采用

范围是已有 GoalCard 派生的单步 `csv.sum` 应用：同卡下一版本、原材料与内容哈希不变，用户明确把一个数值列改绑为另一个数值列。此入口使用原 AppRun Worker、注册工具、独立求和 oracle 和原实例 CAS 采用控制器。模型请求为 0；Goal 的语义适配仍为 UNKNOWN，人工初始 PENDING，内部 Release 未发布。

在“使用已保存的本地应用”选择原 CSV 实例，打开“修订此应用的 Goal 与列绑定”。先打开来源 Goal，明确保存下一版本，再回到该实例读取修订基线。选择旧列和新列，提交修订草案；核对完整 Goal、材料、影响范围后单独确认隔离重验。实际 CHECK 成功后，准备新 Release，单独勾选保存，再读取原实例采用预检并明确采用。之后还需主动启动一个新 Run。

实现边界：

- 原 `app_drafts`、generation 来源及其独立接受账本原样保留。没有创建 executor、runtime、principal 或 Grant。修订仅重建 Goal 内容、两个输入 schema 的列 enum，以及 manifest/action/binding 的 revision；稳定 ID、数据绑定、输出 schema 和历史结果保留。
- proposal、CHECK 接受、CHECKED 证明、Run 引用和 Release 批准复用现有独立双封存请求账本。正文读取前以主体、项目、实例和材料标识的并集鉴权。损坏的接受记录不能成为“未受理”证明。
- CHECK 使用原 Release 的独立实例，与业务实例的数据分离。启动、排队及接受封存同事务完成。CHECK 的角色由接受账本、绑定及事件共同识别，禁止普通使用和版本切换，包括 no-op。
- 每个新 Run 的冻结绑定保存完整 GoalCard v2 快照；FrozenRunContract 的 GoalSpec 冻结该卡身份、目标、约束、未决项。入队、回读、派发及提交均解析同一封存修订，原工具和 oracle 实际重算。旧列在采用后由原 Worker 的严格输入检查拒绝并留下 FAILED 历史。
- 新 Release 保存原 draft，另附精确的修订来源、输入、Goal v2 和实际 CHECK 指纹。来源依赖不可变原 Release 与 CHECK，不沿业务实例的移动指针追踪。采用前的旧 Release 行为保留。
- 新批准及采用重新检查 Goal 当前版本、材料授权、图锚、人工锁、原实例修订和数据版本。原实例采用继续使用原 CAS、兼容 schema 和保留结果检查。未知项目依赖拒绝，应用内未知依赖保留在影响范围，语义不升格。
- 目录使用所选 Release 的列约束；历史 Run 使用自身的 Release。新 Run 的人工声明不继承旧 Run 的 ACCEPTED。Goal 再次变化会阻止新执行/采用，已冻结的历史版本仍可独立读取。
- 页面各阶段单独确认，确认随新证据或映射变更清除。请求按账号、项目和实例保存原键；未知接受只 GET 恢复，迟到响应不得跨账号、项目、实例或工作区安装状态。仅已证明回滚且先前不存在的请求，或已终止的 CHECK，允许明确开始新修订。
- 离开并返回待确认的草案、Release 或 CAS 页面时，先回读当前基线及原键的已接受内容，再恢复完整 Goal、材料、冻结列映射、重验、Release 与保留数据预检；旧勾选不保留。新确认还检查当前实例签名和批准有效期。未知请求保留精确原键，不自动重发；CAS 回读须匹配原批准的实例切换历史。
- 若仅原实例在冻结基线后多了结果，页面展示旧冻结内容与当前结果版本的差异，仅保留明确提交原键 CHECK 的服务端拒绝核查。收到原有未受理、原先不存在且事务已回滚的证明后，才能明确重新准备；不会凭本地缓存创建新键或放行 Release/CAS。

这是一次有界的原始 CSV 应用修订。后续连续修订、自由语言理解、LIVE 模型、材料替换、跨平台限额变化的历史兼容均不在本片验收范围。真实 Windows、PG、远端 CI 和部署的执行情况以证据目录为准，不据本地 mock 结果推定。
