# 同一已采用 CSV 实例的显式材料替换

依据原 V5 产品设计 §9.3、§10.1 和 F2-T07/T08，本片限于已经明确采用列绑定的单节点 CSV 求和实例。用户在“使用已保存的本地应用”选择该实例，点击“更换此实例的已授权 CSV 材料”，读取当前基线，明确选择另一份已具备 owner、项目 runtime 和原 App runtime 精确读取／求和授权的 CSV。新材料须有不同身份和内容哈希，并包含原已采用的有限数值列。本操作不创建 Grant、App、运行身份或新的业务实例。

材料替换保留已采用 GoalCard 的版本、正文和原材料来源；页面分别显示原 Goal 来源、当前执行材料和目标材料的完整 SHA-256。它不声称旧 Goal 已通过新材料的语义验收。更换材料不同时改列或编辑 Goal，当前 Goal head 必须仍与已采用版本一致。

提交冻结 `csv-material-revision.v1` 草案后，各阶段沿用原控制器：单独确认隔离 CHECK，原 NoModel Worker 通过 `data.aggregate_csv` 实际运行并由独立求和 oracle 核对；单独确认创建不可变内部 Release；读取原实例采用预检并明确提交 CAS。采用只移动原实例的 Release 指针及修订号，保留其数据版本和旧结果。用户还需显式运行一次，才产生新材料的新结果和独立 PENDING 人工验收入口。旧 Run 的人工 ACCEPTED 不转移。

原 draft、generation、GoalCard、旧 Release、旧图锚和旧结果保留。有效规格只替换单个 CSV 绑定、内容哈希、资源依赖／权限引用，并递增 manifest、action 和 binding 规格版本；输出 schema 与稳定 App／Action ID 保持。新资源取得新的服务端图节点 ID，其他图节点保留原 ID。影响规划沿原类型边传播；人工锁冲突、未知 PROJECT 依赖、过期批准、Goal／权限／材料／数据版本变化和 CAS 冲突继续拒绝。

新请求先以标量标识联合授权 A、有效父材料、B 及 Goal 来源，再读取私有正文。冷读取、CHECK、批准、CAS 和 Worker 继续重新授权；读取历史不跟随当前实例的新指针。原 v1 Goal 与 v2 列修订仍使用原严格请求模型及哈希；材料合同有独立严格字段，未放宽全局 candidate 来源校验。

页面复用原持久意图和恢复控制器：材料必须手选；阶段确认在离开后重新核对；未知回执只能原键 GET 恢复；双击与迟到回调不得重复提交或跨账号／项目／实例安装状态。未提交草案时可返回当前实例入口；已经受理或接受不明的业务步骤仍须按原键恢复。

这是合成数据的受限 CSV 功能，不扩大为 DAG、通用编辑、工作流逐次材料或真实语义验收。实际通过范围、原始失败和最终源码冻结以本次证据为准；真实模型、真实用户场景、Windows、原生浏览器、PostgreSQL、远端 CI 和部署未据此推定通过。
