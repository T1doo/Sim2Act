# Narrow receipt continuation: conditional design ACK

**Conditional ACK for implementing and reviewing this narrow default-off design; no implementation, arithmetic, test or window acceptance is granted.** Current source baseline is clean HEAD `59bd1b3362f11a95210670d371d621aa89b0546e`. The reviewer only read source and existing evidence; no tests, DB, product, Mock, G0 or signals were executed and no repository files were written.

The smallest justified closure is the single prewrite `_cold_receipts` call between the first and second `_ColdTrialGraph.commit`. It is not postwrite receipt verification or general receipt execution. For the admitted prefix the original pass processes one VERIFIED `resource.read`, then reaches the current non-VERIFIED model operation and stops because its exact operation ID equals `pending_id`, with `allow_pending=False`. It returns the original outputs/proved containers and only then `record_receipts` installs the proof. The original pass, all its validators and checkpoints, and actual proof creation must remain at that original call position.

The following conditions make the design reviewable:

1. Bind an exact original `_ColdBindingGraph`, its exact `_ColdRunFacts`, graph, store/connection/transaction/read token/epoch/thread, job identity/version/fence, original binding and current operation ID. Read the pending ID from the already pinned current call, not an untrusted optimization argument. Pre-read on the same original reader: do not synthesize a replacement reader, raw result, permit or receipt proof.
2. Recognize the complete approved frozen plan/action prefix and original binding relationships; names `read_pick`/`duties_pick` alone do not establish the tool or wiring. Require precisely two operations, unique call IDs and operation IDs, map to plan positions independently of SQL order, the first VERIFIED read and current pending model relationship, no extra/later operation, `allow_pending=False`, and the supported tools count. Check exact native types before shape tests and validate the step anchor's integer fence/range before passing it to `progress_event`. Unsupported private shapes select LEGACY before any owned issuance. They remain accepted or rejected by the unchanged legacy path.
3. For this prefix the complete new raw-reader closure is `receipt_operations`, `intent` for both operations, `has_effect` and `step_anchors` for the verified read, and `progress_event('CLAIMED', validated_anchor_fence)`. Existing `checked_counters` still runs at the original point. Do not call `effect`, pending/model proof producers, `_receipts`, `receipt_for`, `intent_for`, or natural pure execution as preflight substitutes. Do not silently omit any existing raw field or row. Keep all original method post-query/full guards.
4. Freeze the existing receipt-proof list's identity/length `m` and exact two future keys `run-facts:<job id>:receipt-binding:m` and `run-facts:<job id>:receipts:m`. Reserve their construction before allocating variable-length names. At original entry, `_put`, and final registration, revalidate the same live reader/graph/transaction/binding/pending/options/slot and one-use phase. Exact reader provenance passed by the original `_put` is necessary at the frontier gate; merely possessing an allowed string is insufficient. Bind the final proof to the original returned outputs/proved objects and original binding, with the unchanged `pending_id` and `allow_pending`; do not manufacture a proof early or accept copied outputs by equality. Keep root non-rebinding and proof-list consistency rules.
5. Original SQL, guard, lifecycle, authorization, drift, validation and DomainError failures propagate and close the candidate; they must not become unsupported-shape/capacity fallback. Only explicit private representation/capacity failures may select LEGACY before issuance, after the normal complete guard. No fallback/retry after issuance or halfway through the receipt segment.

Early original-reader access is a **change in SELECT/cache-fill and failure timing** when those facts were absent. Same-transaction pinning can justify its data freshness; it does not make the global order identical. The contract must disclose that change. The reader's original `.all()`, DB decoding and row-to-dict materialization occur before the two-operation shape is known. If these remain excluded baseline operations, retain that explicit exclusion and do not claim their allocation is bounded by the native ledger. After obtaining the original list, check length before any new `by_step`/full projection; a fixed two-position scan avoids another unbounded mapping. Any new preflight data construction needs its own reservation.

The current downstream reservation was derived before these new roots and is not automatically sufficient. Before issuance, size all newly prefetched raw roots and charge the complete frontier including their hidden storage, aliases, keys and values. The added reserve must cover at least:

- Exact future names, provenance/state record, mirror/table slots and proof-list growth, resident until scope close.
- Original `resolve`: its data-binding map and argument dictionaries for both prefix steps; `intent_for` input-source deepcopy and predecessor receipt fingerprints.
- VERIFIED read's `natural.pure(resource.read)` full source deepcopy, original `bounded_source` checks, original schema-validation intermediates, actual/wanted receipt structures and both original outputs/proved containers. Inputs may have shared descendants; use a bound compatible with actual copy/JSON behavior rather than assuming tree size equals unique-node count.
- `receipt_for`'s input/output fingerprints, complete stored-vs-generated fingerprints, JSON escaping/UTF-8 and sort-key temporaries, retained hashes and overlapping caller temporaries. Field/step counts can be fixed, but text, integer and source sizes must derive from the admitted complete data. No new arbitrary string cap is justified.
- The new settlement `receipt_for` for the parsed current model response, if not already covered by an explicit original baseline exclusion. The prewrite segment continues past `_cold_receipts` before the second commit; closing only proof registration is not enough to claim the entire remaining continuation budget is proved.

Continue the existing documented exclusion for repeated full CGR/typed validation and original full codec operations only if explicitly stated. Those checks must still serialize/hash fresh complete inputs; the projected frontier must include both newly registered mutable proof roots and independently reachable aliases. Their larger input also changes later frontier extents; no schema or memo identity may be used as cached validation.

Minimum directed evidence should distinguish: shuffled operations; extras/duplicates/non-prefix and other pending IDs selecting pre-issue LEGACY; original revoked/stale/closed/changed-fence errors never downgraded; swapped reader/binding/transaction/proof slot and copied outputs refused; reused/out-of-order proof roots refused; same-aid/non-ID raw mutation refused; low budgets selecting LEGACY before issue but closing without fallback afterward; and unchanged default/post behavior. Actual numerical allocation/work bounds and tests remain for the concrete implementation review. This design ACK does not assert all normal future roots have now been discovered or that G0 will finish within lease.
