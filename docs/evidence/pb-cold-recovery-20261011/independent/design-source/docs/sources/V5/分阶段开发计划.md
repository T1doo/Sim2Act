# Sim2Act V5：分阶段开发计划

> 配套规范：[平台产品设计](平台产品设计.md)。动态总方案入口：[Plan.md](Plan.md)。
>
> 本文按能力依赖与可重复验收组织，不安排日期、工期、成功率、费用或获奖概率。阶段均为【计划】，未取得实现与实测证据。命令、脚本和报告路径是待开发接口，不表示本次文档包已有可运行平台。

## 0. 计划的规范关系

产品文档是范围、对象、状态、权限、Windows 和 API 约束的规范来源；本计划是任务与验收来源。`docs/Fn/Plan.md` 引用相应阶段，`docs/Fn/Log.md` 记录实际执行，不另造一套相冲突的需求。

阶段卡统一包含：**目标、前置条件、任务、产物、通过条件、失败处理**。每个通过结论必须关联环境、输入版本、运行/回执、测试报告和实际代码提交。没有证据时保持 `PLANNED` / `NOT_RUN` / `BLOCKED`，不能以文档已存在代替代码完成。

## 1. 版本、依赖和首版参赛边界

| 阶段/门 | 建设重心 | 阶段结果 | 是否首版必需 |
| --- | --- | --- | --- |
| F1 | Windows 原生底座、对象/权限、持久任务、书生真实接入、固定测试 | 可启动和可核查的基础执行链 | 是 |
| F2 | 两种应用生成、声明式运行、身份与发布、最小依赖修改 | R0-alpha：内部完整闭环 | 是 |
| F3 | 跨任务验收、恢复/撤权/增量验证、独立对照、干净 Windows 复现 | R0：首个可验收版本 | 是 |
| C0 | 赛道规则核实与交付材料 | 首次参赛包 | 参赛必需；不是额外功能阶段 |
| F4 | 更广制作能力与通过隔离门后的代码生成 | 经验证的增强能力 | 否 |
| F5 | 自动触发、复杂增量演进与升级 | 常在线条件下的持续行动 | 否 |
| F6 | 资源分发、协作和跨应用组合 | 可授权复用的生态能力 | 否 |
| F7 | 扩展规模、持续回归和产品维护 | 长期成熟度提升 | 否 |

依赖主线为 **F1 → F2 → F3 → R0 → C0**。F4—F7 是增强分支，不是首次提交前置。F5 的纯声明式自动任务不依赖代码生成，但必须依赖 R0 的身份、账本、停止和恢复语义；F6 跨应用自动触发依赖 F5 的触发控制。未选定或未通过的隔离路线不会阻塞 R0，只使代码执行保持关闭。

R0 必须完成两条不同路径：P-A“目标直接生成应用”、P-B“已完成任务提取应用”，以及一组已声明依赖驱动的局部修改。不能把 P-B、权限和增量能力推迟到 F4/F5 后仍将 R0 描述为完成。

## 2. 全阶段共同执行规则

每阶段先确认产品规范版本和前置证据，再实现最小对象、执行路径与测试，最后更新文档和阶段日志。阶段通过不豁免之前测试；新增入口必须回归现有权限和副作用保护。

每条任务在阶段 Plan 中至少保留 `task_id`、目标、依赖、触及契约、产物、测试 ID、状态和证据引用。Log 只追加实际变更，不预写“已完成”“提升多少”等结论。

报告至少分开记录：工程确定性测试、真实模型测试、故障注入、用户任务评价。模拟器通过不能证明账号接入，Linux/WSL 测试不能证明 Windows 原生，历史回放不能算实时执行。

预算尚未明确时先锁定试验所需的请求/Token/工具次数上限并获得确认；不是凭空安排一笔总费用。没有用量上限的任务不得开启无限规划或自动重试。

## 3. F1：Windows 原生底座与可核查执行

### 3.1 目标

拉取指定提交后，能在目标 Windows 原生环境按说明启动 API、独立 worker、数据库与界面；真实书生调用能提出并调用可信工具、读取反馈并修订结果。建立后续应用所需的契约、身份、账本和测试，而不是先做空控制台。

### 3.2 前置条件

V5 两份文档已确认为当前设计基线；具备目标 Windows 版本、安装权限与本地数据库条件；书生账号待配置。缺少账号可继续工程实现，但真实模型验收标为 BLOCKED，不能宣布 F1 全通过。

### 3.3 任务

| ID | 任务 | 具体产物与边界 |
| --- | --- | --- |
| F1-T01 | 建立文档与数据契约 | GoalSpec、ActionSpec、AppManifest、Run、Operation、Grant、Approval 的最小 Schema；枚举与产品一致 |
| F1-T02 | 原生启动链 | PowerShell 环境检查/安装/启动/状态/停止/测试接口；API/worker 独立进程、PostgreSQL 服务和文件目录；精确依赖锁 |
| F1-T03 | 三工作区骨架 | 项目可创建并查看真实任务；应用仅展示真实状态；资源按材料/能力/连接分类，无假功能入口 |
| F1-T04 | 身份与可信动作网关 | 本地身份初始化、项目范围、注册工具、有效权限交集、服务端输入校验、资源逻辑 ID |
| F1-T05 | 持久任务和操作账本 | 接受后持久化、队列领任务、租约与 fencing token、独立心跳、步骤/尝试/回执、暂停和取消意图 |
| F1-T06 | 书生适配与统一限流 | 非流式工具循环、默认配额主体、正式模型能力探针、结构与错误校验、进度保存、统一用量记录 |
| F1-T07 | 固定测试资产 | 创建 AT-01—AT-28 的规格、夹具和重置机制；F1 执行早期子集，未实现部分明确 NOT_RUN |
| F1-T08 | 冻结环境与待确认清单 | 记录 OS/依赖/端口/数据位置；账号额度、上游限制、真实任务材料授权与预算边界待核实 |

ActionSpec/AppManifest 在这里建立可验证的最小结构，F2 必须真实使用。任务暂停、取消、worker 失联和结果不明从此阶段起有明确枚举，不能先以一个 `failed` 字段混过。

### 3.4 产物

可启动骨架及源码、依赖锁文件、Schema 草案与验证器、受限工具目录、权限与操作账本、Windows 运行说明、`capability-report`、AT 固定测试规格、`docs/F1/Log.md` 中的真实记录。

### 3.5 可重复验收与通过条件

执行 AT-01—AT-08。先安装与启动，再用同一输入重复运行指定测试，保留 Run/Operation ID 和数据库/文件回读。真实模型至少完成目标理解、工具选择、工具结果回填以及一次工具反馈后的修订，不只测试“你好”。

Schema、跨项目拒绝、持久化、基本恢复和授权检查的固定工程用例必须全部通过。账号测试必须有真实记录，缺账号不能以 mock 放行。故障注入可验证限流/截断逻辑，但报告明确注入来源。

### 3.6 失败处理

原生依赖无法启动时记录原因并修正安装路径，不能用远程浏览器或 WSL 成功替代；确需改变主平台必须先作设计决策并重新验收。API 参数不兼容时收紧白名单，不切换到开发所用模型冒充书生。任何越权、秘密泄露或重复副作用阻止进入 F2 发布链。

## 4. F2：两条生成路径与最小增量闭环

### 4.1 目标

从目标或已完成任务生成可处理新输入的声明式应用，同时具备最小依赖修改能力。阶段结束交付 R0-alpha，不等待任意代码执行、自动触发或生态组件。

### 4.2 前置条件

F1 通过，Schema 与可信目录有版本；运行身份和 Grant 可以实际执行；独立验收已建立；Windows 与真实书生链可用；应用仅使用产品 §3 的 R0 输入、输出和动作范围。

### 4.3 任务

| ID | 任务 | 具体产物与边界 |
| --- | --- | --- |
| F2-T01 | 目标卡和验收契约 | 已知/假设/未决项分离；模型不能自行降低硬条件或检查 |
| F2-T02 | 实现 P-A | 目标 → 规划 → 清单 → 编译/验证 → 应用；记录自主工具选择和必要介入 |
| F2-T03 | 实现 P-B | 从已成功任务提取变量/逻辑/模型节点；移除原会话及固定路径依赖；单独冷会话验收 |
| F2-T04 | 声明式应用运行器 | 有限 DAG、受控分支、可信组件、固定动作引用；服务端严格结构和输入输出校验 |
| F2-T05 | 身份与统一入口 | 绑定最小应用 Principal/Grant；页面与内部 API 走相同动作网关；禁止 Manifest 自授权限 |
| F2-T06 | 真实成果与本地数据 | 文件、结构化结果、受控视图、本地记录写入；资源和结果可回读，不用静态样例替代 |
| F2-T07 | 最小交付图和局部修改 | 稳定 ID、类型边、指纹、依赖失效、未知依赖保守重验、人工锁定冲突 |
| F2-T08 | 预览、发布和数据分离 | 测试命名空间、不可变 Release、实例数据、兼容升级、批准指纹和版本比较 |
| F2-T09 | 扩展可靠性实际链路 | 对正在运行的应用验证暂停/取消/失联/撤权/幂等与结果不明，不能只测函数 mock |

P-A 与 P-B 可共享编译、发布和运行器，但必须有分别的功能入口与来源记录。R0-alpha 的应用并非只保存一个提示词，必须有输入、执行、结果和检查。

### 4.4 产物

可生成的 ActionSpec/AppManifest、运行器和可信组件、P-A/P-B 各自的真实输入与结果、最小 DeliveryGraph、局部补丁和验证记录、发布/实例存储、应用使用页面及使用范围说明。

### 4.5 可重复验收与通过条件

回归 AT-01—AT-08，执行 AT-09—AT-22。P-A 不允许依赖一份手工搭好的同款清单充当生成；P-B 在无原会话的新运行中读取新资料，不能返回原任务缓存。

两条路径都检查正常输入、未见输入与错误输入。局部修改至少包含确定依赖、未知依赖扩验和人工锁定三个类别。已知应保留对象的 ID 与内容指纹须保持；应变化对象和检查确实更新。

页面/API 不能绕过权限；预览不污染实例；同一请求重复提交不重复写入；发布兼容性未通过不得切换。输出结果不仅存在，还必须由固定 oracle 验证内容或状态。

### 4.6 失败处理

只能生成静态页面时记“应用运行未通过”；只能从目标生成时 P-B 保持未完成；只能全量重做时记“增量未通过”。不得把缺失能力移到 F5 却继续宣称 R0-alpha 完整。

无法表达的需求返回范围缺口，不启用任意代码补救。权限或本地数据一致性失败立即阻止发布；仍可保留安全的草案。未知外部效果必须等待核对，不能通过清空 Run 重试消除记录。

## 5. F3：首版独立验收、真实任务与 Windows 复现

### 5.1 目标

在不增加能力清单的前提下，把 R0-alpha 验证成 R0。确认通用机制在不同任务类型下可用，并得到可追溯的完成、正确性、介入、耗时和用量记录。

### 5.2 前置条件

F2 闭环完成；开发用例与冻结评价用例已隔离；获得的真实材料有明确授权；预算/重试/停止规则确定；验收者能独立核查关键结果。真实样例不足时如实阻塞实用性证据，不伪造用户或业务成效。

### 5.3 任务

| ID | 任务 | 具体产物与边界 |
| --- | --- | --- |
| F3-T01 | 固定测试全量回归 | AT-01—AT-27；覆盖 Schema、身份、持久化、恢复、错误输入、修改与版本 |
| F3-T02 | 跨任务类型验证 | 对资料/内容、结构化数据、本地记录等不同真实任务使用同一运行器；任务不是产品栏目 |
| F3-T03 | 独立 oracle 与评价 | 确定性结果独立计算；语义内容使用固定量表与来源核对；模型不能降低标准 |
| F3-T04 | 公平基线与消融 | 同书生模型、工具、组件、权限和预算；分别比较两生成路径、新输入与局部修改 |
| F3-T05 | 可靠性与未知用量核对 | 崩溃窗口、fencing、重复提交、撤权、取消、截断、缺失 usage；把失败成本纳入账本 |
| F3-T06 | 干净 Windows 原生复现 | 新环境/用户目录按说明安装启动；确认浏览器关闭、后台停止、重启后的不同语义 |
| F3-T07 | 首版证据冻结 | 源码提交、依赖、Manifest、模型能力快照、测试数据、结果、限制与文档同时锁定 |

不追求为了首版增加更多页面、行业模板或外部连接器。此阶段价值是消除假运行、未知失败和不可复现，而不是扩大宣传范围。

### 5.4 产物

R0 候选版本、Windows 环境与复现报告、固定测试报告、两条生成路径与各任务族结果、基线/消融输出、原始运行与用量账本、失败分析、用户反馈和已知限制。

### 5.5 可重复验收与通过条件

固定工程安全与一致性检查必须全部通过；任何跨项目访问、明知未知却重发副作用、丢失业务数据或测试标准被降级，都阻止 R0。

两条生成路径均需有完整成功的实时运行记录，且规定的新输入/错误输入/局部修改病例经过独立核对。不同任务类型分别报告结果，不把某一类型的成功覆盖另一类型的失败。记录真实评价集的全部结果；模型总体完成率不预先填数字，也不由成功案例挑选决定。

Windows 原生复现必须真的在声明的 OS/依赖组合完成。实测结果、失败、介入与成本可以追溯到具体运行和提交。只做了文档检查、Linux 单测或历史回放不能通过此门。

### 5.6 失败处理

任何硬门失败则修复并重新跑相关及全局不变量；不能改名为“后续增强”绕过首版责任。真实任务材料不足时可标记工程 R0 候选，但 C0 实用性证据仍阻塞。

若模型只能在部分支持范围内稳定完成，收紧范围需明确更新目标和适用输入，并重新评价新版本；保留旧版本失败记录，不追溯修改评价结果。

## 6. C0：首次参赛交付门（不要求 F4—F7）

### 6.1 目标与前置条件

R0 已有真实测试与复现记录；当前赛道规则已核实到足以提交。预算、截止时刻、体验方式等尚未确认项不能被默认值悄悄替代。

### 6.2 任务与产物

| 任务 | 产物/核查 |
| --- | --- |
| 确认方向与身份 | 方向3、个人参赛信息、官方要求及最新通知的留存 |
| 确认日期与入口 | 准确截止日期、时刻/时区；应用体验链接的接受形式和访问权限 |
| 核实托管模型交付 | 赛方对 API 模式下模型文件/权重说明的答复；实际模型 ID、配置、官方权重来源与许可 |
| 技术文档 | PDF：痛点、范围、方案、书生真实链、契约与可靠性、对照与限制、运行步骤、相关链接 |
| 视频与体验 | 不超过5分钟、不低于720P的视频网盘链接；可访问应用体验入口，不能以本机 localhost 冒充公网链接 |
| 代码与复现 | 源码、依赖锁、启动脚本、Windows 说明、模型使用说明、数据和测试结果、许可清单 |
| 包与权限检查 | 按要求外层 ZIP 和内层关键代码/模型说明 ZIP；校验完整性、链接、访问期限、无密钥/敏感数据 |

### 6.3 通过条件与失败处理

执行 AT-28。材料描述与实测范围一致，技术文档存在，代码与环境能够复现，视频和应用链接以接收方身份可访问，模型文件条款处理方式得到确认或按正式规则提供。

体验链接形式、托管权重要求、最新截止等关键事项未核实则保留 BLOCKED，不能写“已满足”。尚未完成的增强能力只进后续计划。C0 文档编写不是新增产品功能，也不要求先完成七阶段。

## 7. F4：能力增强与隔离代码执行门

### 7.1 目标

在 R0 的契约和可靠性上扩展 V4 已有的研究、格式、制作及特殊逻辑能力。只有通过独立隔离门，才允许模型生成的代码被执行。

### 7.2 前置条件

R0 通过；新能力有明确需求和输入输出边界；隔离候选有部署位置、成本/账号条件和权限说明。不得要求 R0 用户先安装某个未验收执行环境才能继续使用基础应用。

### 7.3 任务

| ID | 任务 | 具体约束 |
| --- | --- | --- |
| F4-T01 | 扩展可信工具/格式 | 新格式有解析失败、来源/截断和许可规则；新增组件依旧由 ActionSpec 驱动 |
| F4-T02 | 隔离选型 ADR | 比较独立虚拟机/远程执行器/受控容器，明确威胁模型、网络、文件、资源、凭证和宿主控制边界 |
| F4-T03 | 沙箱原型与拒绝测试 | EX-01：越权读取、秘密外传、资源耗尽、越界网络、残留与逃逸测试；拒绝共享主进程/宿主控制权 |
| F4-T04 | 受控代码构建 | 锁定语言/依赖，代码先生成文本再进入隔离构建与独立验收；失败保持未执行/未发布 |
| F4-T05 | 能力注册和回归 | 新执行器仅由管理员审查注册；EX-02 与全部 R0 安全用例回归 |

### 7.4 产物

选型决策、隔离部署/威胁说明、可核查测试记录、经审查的扩展工具和能力包、更新的适用范围。未经证实的“绝对沙箱安全”不属于产物。

### 7.5 通过条件

EX-01—EX-02 通过，生成代码无法访问平台密钥、其他项目、数据库全权角色或容器控制接口；资源和生命周期限制有效；新成果仍能按既有契约验证与发布。远程路径需明确数据发送范围和真实运行成本。

### 7.6 失败处理

隔离门失败即关闭代码执行，不以杀掉进程或 Docker 名称代替安全边界。可以仅发布通过验证的可信工具增强；R0 声明式能力继续保留。

### 8.2 前置条件

### 8.6 失败处理

## 12. 数据、对照与指标口径

### 12.1 数据组织

开发集用于调整提示与工具；冻结评价集在基线版本和预期结果确认后锁定。相同来源任务的改写不得拆到两边造成泄露。真实、公开、合成数据分别标记；真实数据不足时说明，不补假用户。

测试结果依据独立数值计算、原始材料及人工确认目标建立。模型可以参与提出测试候选，但最终验收不能由同一生成器任意决定。

### 12.2 对照组

| 对照 | 保持一致 | 主要问题 |
| --- | --- | --- |
| B0 通用执行智能体 | 同书生模型、工具、组件渲染、权限、输入、可用信息和合理预算 | 平台组织方式能否提高交付正确性和减少人工拼接 |
| B1 重复对话 vs 应用复用 | 同任务序列和新输入；计入初次生成/验证与后续修复 | 是否减少重复描述和重新配置，总投入何时有改善 |
| B2 全量重建 vs 依赖修改 | 同一个起始应用、要求变化、工具和安全策略 | 漏更新、误改、回归质量与总成本如何变化 |
| 消融 | 移除交付关联或应用化等专有机制，其余资源相同 | 哪个机制提供了实际收益 |

基线也能使用基础组件和工具，不因为缺渲染器就被判“不能交付应用”。不得关闭安全校验来让某组更快。实验顺序、缓存、模型配置和预算均记录；无法完全控制上游模型版本时明确局限。

### 12.3 指标定义

| 指标 | 口径 |
| --- | --- |
| 完成率 | 满足预先约定必需交付的任务数 / 全部纳入任务数；部分完成单列，不删失败 |
| 正确性 | 独立断言/量表结果；发布、输入、运行结果分别报告，不用字数替代 |
| 新输入复用 | 新输入的实际结果及额外配置/说明；原始任务重放不计入 |
| 人工介入 | 澄清、批准、修正、手工连工具、恢复操作的次数与主动用时，必要审批单列 |
| 端到端耗时 | 接受至终态的总历时；排队、模型、工具、验证、修复与等待人工分项 |
| 总用量 | 首次构建 + 各次运行 + 失败 + 重试 + 验证 + 修复；包含调用/Token/工具耗用 |
| 用量完整性 | 已知/部分/未知字段与上游可核对账单；未知不记零，单价未知不折钱 |
| 漏更新 | 独立应更新集中未正确更新对象数及比例 |
| 误改 | 独立应保留集中无必要被改对象数及比例 |
| 可靠性 | 失联恢复、重复请求、撤权、结果不明的正确处置与副作用记录 |

样本分母为零则 N/A；小样本报告原始数量、分布和不确定性，不追求好看的百分数。模型别名不能保证权重不变，保留模型列表、返回 ID、日期与配置。

### 12.4 用量与预算不是承诺

30 RPM / 120 秒限制属于当前官方托管说明，不是本项目吞吐量或处理时延承诺。具体账号和任务预算待确认。多个任务、验证器与修复共享上游配额；模型调用失败、响应丢失可能仍产生用量，需要保留未知成本而非认定免费。

后续仓库还应实现 `tests/`、`scripts/`、配置与证据输出目录；这些不是本次设计文档包已实现的软件。

### 14.1 状态与更新规则

阶段/任务状态为 `PLANNED`、`IN_PROGRESS`、`BLOCKED`、`READY_FOR_REVIEW`、`ACCEPTED`；测试结果为 `NOT_RUN`、`PASS`、`FAIL`、`SKIPPED`。SKIPPED 必须有原因，不算通过必需门槛。

修改范围、Schema、状态机、权限或验收时同步更新两份总文档、影响阶段 Plan、测试定义和决策记录。实际源代码引用以真实 commit/PR 为准，不能用本次文件版本号假装代码提交。

### 14.2 日志最小模板

```text
记录 ID / 实际时间 / 操作者 / 阶段与任务 ID
基线：设计版本、代码提交、环境与依赖
实际变更：改了什么，为什么改；是否改变承诺范围
测试：测试 ID、命令、输入 hash、运行/操作 ID、报告位置
结果：PASS/FAIL/SKIPPED，实际输出、失败与未知项
决策：考虑过的方案、选择原因、风险和后续处理
引用：真实 commit/PR；没有则“未提供”，不可编造
```

初始 Log 保持“尚无实现和测试记录”；可以记录文档模板初始化，但不得提前写产品测试通过。动态 Plan 负责状态摘要，Log 保留事实和原因。
