# Enforce the original finite interval at the actual SQLite commit boundary

Original lifecycle review found no deliberate expired-lease revival: claim starts30 seconds after queue/scope work; heartbeat checks the still-live old lease and CAS before publishing committed renewal; only an explicitly signed SQLiteSettlementCaps contract allows one120-second received-attempt settlement. G0, admission wait and G1 share that original120 seconds. Writer admission/first-DML has its own30-second bound; it is not a whole-G1 limit. No cap, timeout, original full graph check, permission/revocation guard or atomic write set is reduced or extended here.

A **real-clock small SQLite counterexample** on source `e7b0916b12e7459fed5c90f5502dde5d7c148420` established a late gap: a commit callback began before a0.15-second original token, waited0.2 seconds, and ended after both clocks expired; the old transaction still persisted `expired-commit` and reported COMMITTED. This component is not a large Cold performance measurement. It makes zero model requests.

The per-engine SQLite delegate now has a private, strongly held registration for the exact driver/Connection/Transaction and this scope's check/clock functions. The callback/control check executes **after SQLAlchemy Connection commit callbacks** and before the captured original DBAPI commit delegate. The post-check tail verifies transaction still active, current data-change count and write sentinel, held owner/roles and delegate. The last clock role then checks original stop/scope and both original deadlines. It does not call the30-second admission `remaining()`.

During this finite commit window, additional SQLAlchemy writes are refused; a callback cannot modify previously verified rows. Checks cannot remove/restore the sentinel and write, replace this invocation's captured tail/clock role, or catch a recursive commit failure and revive a rolled-back transaction. The busy state is private per-engine, not a mutable Entry permission. Registrations are removed precisely on exit, so pool reuse and ordinary commits do not inherit a verdict or guard. Ordinary raw SQLite dialect protocol remains compatible.

**Supported domain is explicit:** finite commits refuse Engine-level commit listeners and echo/logging callback paths. SQLAlchemy runs those after Connection listeners, so silently accepting them would permit a callback to replace the delegate after the tail check. This round does not reorder global Engine dispatch, skip callbacks, disable logging or change configuration. Connection callbacks may observe/read/control time but cannot write after final proofs. Ordinary transactions without a finite guard retain their Engine callbacks. Arbitrary direct raw commits, unknown private engine mutation and elapsed time *inside* the captured DBAPI commit/fsync cannot be retroactively rolled back and are not claimed covered. This is a last pre-delegate admission check, not a promise to undo a durable commit.

On a rejected finite commit, SQLAlchemy may already have deactivated its RootTransaction. Explicit raw rollback is therefore necessary; if rollback or exception cleanup fails the connection is invalidated and the original rejection remains primary. Snapshot listener removal and busy-timeout restoration cannot mask it. Ordinary no-guard exception semantics remain unchanged. A successful delegate commit is tracked separately from cleanup errors; evidence must not falsely report an already committed transaction as rolled back.

The actual default writer wires its original interval/stop into this boundary in both local snapshot and ordinary SQLite writer modes. Booking the extended interval likewise rechecks the **old** still-live lease, stop and monotonic booking bound immediately before its commit; a stopped/expired booking cannot publish an extension. Legacy non-snapshot callers still ignore the old optional snapshot token unless the original writer explicitly supplies a finite check. PostgreSQL behavior is unchanged and unverified here.
