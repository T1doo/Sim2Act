# 四步文本应用的同 Run 报告与人工声明

本片接续原 V5 §4、§11 及 F2-T05/T06：已保存的四步文本应用原可实际执行读取、两次独立字面检索和条件引用报告；现在从统一目录选择应用与实例，明确提交两次检索词和报告分支后，可在同一成功 Run 阅读完整报告、两组原文引用、行号、材料 SHA-256 与结果版本，并逐项作出人工声明。

人工声明另行读取精确证据、准备 15 分钟预览，再为完整 Goal 的标题、目标、已知、假设、未决项、硬条件和验收检查逐项选择接受或拒绝并填写理由，明确提交。声明只属于该主体、项目、实例、Release、Run、输入、材料、Goal 版本及 typed 结果；新 Run 默认为 PENDING，旧声明和结果保持历史。字面核对 PASS、合成 ACCEPTED 与真实语义验收分别保留，正式发布关闭。

新 `owner.text-four-step.v1` 适配器复用既有 `text_workflows.verify_job`、逐 Run 双 seal 账本和 `scoped_run_submit`，不新增 executor、Grant、模型调用、业务记录 writer 或数据 schema。四步输出的 `resource_id` 是源材料而非保存成果，不能套用自然规范成果的保存权限或 `SPEC_COMMITTED` 证明。旧自然规范声明端点也在账本与原 key 短路之前检查所属家族，防止借共享存储跨家族操作。

仅完整 SUCCEEDED 报告可准备声明。未选报告的运行仍为 PARTIAL，保留实际三步和报告跳过证明，不创建成功结果或人工签收。新运行未终止、实例 Release／修订／结果版本变化、Goal head 变化、来源漂移或当前权限失效时，拒绝新的决定；本人仍可只读取已有声明元数据并明确取消或撤回。原 key 绑定精确请求，回执未知时只用原 key GET 恢复，不因切换页面或双击重发。

PARTIAL 不覆盖实例已有的成功报告；用户可明确重新选择仍为当前 typed 结果的成功 Run。选择 PARTIAL 时清除旧报告与人工状态，不把旧声明呈现为本次验收。

本轮仅以合成数据、实际 TestClient HTTP、正常 NoModel Worker 和生产页面脚本验证本片。实际冻结提交、执行分批、原始失败、独审范围和未运行项以同轮证据为准。不代表完整 T06、P-A/P-B、真实用户语义、Windows、原生浏览器、PG、远端 CI 或部署通过。旧满盘环境最后独审报告缺失及旧取消项的 NOT_VERIFIED 状态保持原证据边界。
