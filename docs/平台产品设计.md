# Sim2Act V5：平台产品设计

> 产品主张：让想法成为会行动的应用。
>
> 核心链路：想法 → 方案 → 制作与验证 → 可用交付 → 可重复运行 → 可验证修改。
>
> 本文是动态设计规格，不是实现报告。当前只审阅了 V4 两份设计和用户反馈，未取得产品代码、真实账号调用或 Windows 运行证据。除“文档已修订”之外，功能统一标记为【计划实现】，账号能力、兼容性和效果标记为【待验证】。

配套文件：[分阶段开发计划](分阶段开发计划.md)；动态入口：[Plan.md](Plan.md)。

## 0. 文档控制与证据边界

**版本：V5 / 契约目标版本：1.0-draft。** V5 修订 V4 的范围、依赖和执行规则，不改变通用平台定位，不增加第四个一级工作区。V4 的能力蓝图保留，但不能再把蓝图能力与首版承诺混写。

本文件是产品范围、对象契约、权限、运行状态和验收语义的规范来源。配套计划负责阶段任务、测试编号、通过条件和失败处理。发生冲突时暂停相关实现，先修订这两份文件；不允许两个互相矛盾的约定同时有效。

证据分为四层：

| 标签 | 来源与能支持的结论 | 不能据此声称 |
| --- | --- | --- |
| 【源文要求】 | 用户提供的 V4、当前反馈和赛题文本 | 已经实现、已取得真实业务成效 |
| 【官方文档已核查】 | 本次查阅的托管 API、模型列表、Windows/WSL、运行框架和数据库文档 | 具体账号已开通、软件在本机已通过验证 |
| 【设计决定】 | 本版明确选择的首版范围、架构、契约和门槛 | 行业首创、适用于任意应用 |
| 【实测证据】 | 后续实际命令、环境、输入、回执、测试结果和提交引用 | 未测试环境与场景也具有相同表现 |

外部文档核查基准为 2026-10-05。账号额度、接口行为和赛事安排仍需在实际实施与提交时复核。阶段计划不设日期、工期、总预算、成功率或获奖概率。

## 1. 共同痛点与平台价值

### 1.1 解决什么问题

**一次性任务完成后，用户仍需反复描述需求、手工拼接工具、重新验证结果，修改要求时又容易破坏已有成果。**

这是一项来自用户反馈、需要实际任务验证的产品问题假设，不是已经完成市场调研的结论。Sim2Act 的目标是把这类工作沉淀为可重复使用、可验证、可演进的轻量应用。

“通用”表示使用统一的目标、动作、数据、界面和验证机制处理不同类型的任务，而不是承诺任意想法都能自动实现。支持边界由可信工具、声明式清单表达能力、权限和输入范围共同决定，不由某个行业名称决定。

### 1.2 痛点—机制—证据

| 共同痛点 | 平台机制 | 后续应观察的证据 |
| --- | --- | --- |
| 新输入到来就重新解释目标和格式 | 保存目标规格、参数与应用清单 | 重复描述量、重新配置操作数、人工主动用时 |
| 多个工具和结果要手工串联 | 有类型的 ActionSpec 和应用运行器 | 真实动作完成情况、手工拼接与返工次数 |
| 每次都要重新判断是否正确 | 固定验收契约、独立验证器、运行回执 | 正确性、漏检、验证成本和必要人工介入 |
| 一处修改导致别处失配或丢失 | 交付图、稳定 ID、保守影响分析、锁定冲突处理 | 漏更新、误改无关内容、人工恢复量 |

平台交付包括本次结果和可重复使用的能力。只需要文件的目标可以只交付文件；需要持续使用的目标应生成可运行应用。没有任何理由强迫每个任务都生成网站。

### 1.3 通用能力如何验证

使用不同类型的真实任务验证相同机制，例如资料整理与带来源的内容生成、结构化数据处理与报表、本地记录收集与状态流转。它们是测试任务族，不是产品栏目或行业边界。

真实任务应来自有权使用的材料，记录来源、脱敏和同意范围；尚未取得时明确写“待取得”。公开、合成、授权真实数据分开统计。不得把自编样例称为客户项目，也不得以少数任务通过推断任意应用可生成。

## 2. 信息架构：项目、应用、资源

| 一级工作区 | 核心对象与操作 | 首版应呈现的真实状态 |
| --- | --- | --- |
| 项目 | 输入想法、附加材料、查看目标卡、制作成果、应用化、提出局部修改 | 未开始、运行、等待、部分完成及成果验证状态 |
| 应用 | 打开已发布应用、输入新资料、触发动作、查看历史结果、继续改进 | 发布版本、连接/授权缺口、worker 可用性、每次运行结果 |
| 资源 | 材料、可信能力、连接三个筛选类别；管理来源、版本与授权引用 | 可用、失效、未配置、已撤回；不能用空按钮伪装能力 |

项目使用“指令区 + 成果画布”，详细来源、调用、验证和版本放在按需打开的侧栏。成果画布是对象视图，不要求用户绘制工作流。应用以实际使用界面为主，管理功能内嵌。账号和平台设置不新增工作区。

一个项目可有多个成果和应用；每个应用绑定一个明确发布版本及独立运行实例。修改应用回到项目草案，不直接修改线上版本。资源引用必须明确授权，同一用户的两个项目也不能默认共享全部材料。

**首版界面没有自动触发、插件市场或公开分享的假入口。**长期能力只在说明或禁用状态中标出，不显示为已实现功能。

## 3. 长期蓝图、首版范围与不支持项

### 3.1 版本与阶段关系

- **R0-alpha：F2 内部闭环。** 两种应用生成路径、最小声明式应用运行、最小依赖更新已经贯通，但不等于满足完整首版验收。
- **R0：F1—F3 通过后的首个可验收版本。** 保留通用定位，完成规定的运行、验证、Windows 复现与故障检查。
- **C0：独立的参赛交付门。** 在 R0 基础上准备赛道证据与材料；不要求完成 F4—F7。
- **F4—F7：后续增强。** 任一增强未通过门槛时保持关闭，不影响如实交付已通过验收的 R0。

R0 和 C0 的准入以检查结果为准，不以“七阶段完成百分比”或预设日历为准。

### 3.2 保留 V4 能力，但明确承诺级别

| V4 能力 | R0 必须实现 | 后续增强 | R0 不支持 / 必要依赖 |
| --- | --- | --- | --- |
| F01 想法理解 | 目标卡、约束、未决项、验收契约 | 更复杂偏好与方案比较 | 不自动改写硬性要求 |
| F02 研究与知识 | 授权 TXT/MD/CSV/JSON 的读取、定位、版本 | 公网检索、更多格式、知识集合 | 不承诺扫描件、任意网址或所有多模态资料 |
| F03 自主规划 | 有预算的工具选择、步骤和反馈修订 | 并行、复杂分支与更长任务 | 无界循环与无预算运行不支持 |
| F04 自主制作 | 可信组件、注册工具、受限模型节点 | 特殊代码生成；隔离门通过后开放 | 禁止任意代码、包安装、Shell、自由 SQL |
| F05 多形态交付 | MD/JSON/CSV、受控文本/表格/简单图表视图、运行结果 | 更多文档与多模态成果 | 不承诺任意格式或独立部署的全栈代码 |
| F06 局部修改 | 已声明依赖传播、保守重验、人工锁定冲突 | 复杂语义/布局变更、协同冲突 | 不支持自动解决所有未知依赖 |
| F07 应用生成 | 目标直接生成声明式应用并发布 | 更丰富应用形态和导出 | 非任意软件生成器 |
| F08 任务应用化 | 从已完成任务提取变量、步骤与检查，验证新输入 | 多轨迹归纳与更广泛泛化 | 不把一次轨迹重放当成应用 |
| F09 统一动作入口 | 页面与受鉴权内部 API 使用同一 ActionSpec | 应用对话、外部 API、更多触发入口 | 不开放匿名执行或自主提权 |
| F10 自动运行 | 手动异步任务、可靠状态与恢复 | 定时、事件、Webhook | 不提供关机后本地继续执行 |
| F11 发布维护 | 不可变发布、实例数据分离、预检、兼容性拒绝 | 复杂迁移与发布策略 | 不自动执行破坏性迁移 |
| F12 验证修复 | 独立验收、有限修复、失败明确 | 更广验证器和压力测试 | 不能降低测试以显示成功 |
| F13 记忆 | 项目内已确认规则、来源和决定 | 可授权跨项目偏好 | 不自动训练新模型或跨项目泄露 |
| F14 资产复用 | 材料/能力引用、版本与权限 | 包分发、协作、跨应用组合 | 不加载未经审查的第三方可执行插件 |

R0 的真实 Act 能力包括生成并保存成果、用新输入重新处理，以及在授权的应用实例中读取/写入本地结构化记录。任意第三方写入不列为 R0 功能；外部动作的结果不明语义先用受控故障服务验证，不冒充真实集成成效。

### 3.3 R0 的表达边界

输入为有类型的表单字段和项目内资源引用。输出为结构化数据、受控成果引用、文本/表格/图表展示及本地记录状态。界面由可信组件目录组合，动作由注册工具和受限模型节点执行。

工具缺失、清单无法表达、数据未授权或关键约束无法满足时，返回 `UNSUPPORTED_CAPABILITY` / `NEEDS_INPUT` / `PERMISSION_DENIED` 等明确缺口，保留已完成成果。不自动启用代码生成兜底，也不为了交付而默默缩减目标。

生成方案仍由模型负责，不是固定按“读文件—写报告—做网站”执行。R0 的工具和组件有范围，但工具选择、参数映射与反馈修订必须是实际书生调用的结果。

## 4. 两条生成路径必须分别实现和验收

### P-A：从目标直接生成应用

用户输入目标与资料 → 形成 GoalSpec 和验收契约 → 书生选择可用工具与交付结构 → 生成并校验 ActionSpec / AppManifest 候选 → 为应用绑定最小运行身份与授权 → 隔离预览、新输入和错误输入验证 → 发布 → 从“应用”使用。

不得要求用户先手工编辑 JSON 或源代码，才把流程算作自主交付。需要人工确认目标或权限是合法介入，但必须记录介入内容与用时。

### P-B：从已完成任务提取应用

先完成真实任务并保存工具轨迹、输入输出和检查 → 识别可变输入、稳定步骤、必要模型判断、输出与写入范围 → 消除原会话和一次性文件路径的隐含依赖 → 生成同一套 ActionSpec / AppManifest → 使用未见输入、错误输入和冷会话测试 → 发布。

P-B 不要求复用之前模型的隐藏推理；应基于明确目标、输入输出、工具调用和验证记录。若仅有一次成功而无法识别稳定逻辑，可交付候选或要求澄清，不能标记为已验证通用应用。

### 共同完成条件

两条路径最终进入同一个运行器、权限网关和发布流程，但测试分别计分。P-A 成功不能代替 P-B 成功，P-B 不能只回放原始结果。

发布应用的适用输入范围、所需模型/连接、验收范围和限制必须可见。新输入运行创建新的 AppRun 和结果版本；历史结果不得被当作当前结果。

## 5. 首版运行契约

以下是【设计决定】，须在 F1 形成 JSON Schema 和测试，在 F2 用于实际生成和执行。只在文档中出现字段名称不算完成。

### 5.1 核心对象

| 对象 | 必须保存的要点 |
| --- | --- |
| Project / GoalSpec | 服务端生成的稳定 ID、所有者、目标与约束、验收版本、引用资源、未决项 |
| Artifact / Resource | 对象 ID、项目范围、修订号、内容指纹、来源定位、验证状态、逻辑存储引用 |
| ActionSpec | 输入输出、执行器、依赖、权限需求、副作用类别、限制、验证器 |
| AppManifest | 应用输入输出、视图、流程、动作绑定、数据范围、身份需求、运行限制、检查与锁定依赖 |
| AppRelease | 不可变清单指纹、ActionSpec/工具/提示/检查版本、验证证据、兼容数据版本 |
| AppInstance | 应用实例与业务数据命名空间；不随发布替换而清空 |
| Run / Step / Attempt | 运行与步骤、每次尝试、租约/取消意图、输入快照、模型与工具用量 |
| Operation / Receipt | 逻辑操作 ID、请求指纹、外部或本地回执、已知/未知结果与核对方式 |
| Principal / Grant / Approval | 调用身份、运行身份、对象范围、有效期、撤回版本、批准的精确变更 |
| DeliveryGraph / CheckSpec | 稳定节点、类型化依赖、影响确定性、验收来源、检查结果 |

### 5.2 ActionSpec 最小契约

| 字段 | 语义与执行规则 |
| --- | --- |
| `schema_version`, `action_id`, `revision` | 协议版本、稳定逻辑 ID 与不可变修订；ID 由平台分配 |
| `input_schema`, `output_schema` | 服务端强校验；引用文件必须是资源 ID，不接受任意本机路径 |
| `executor.kind` | 仅 `registered_tool` 或 `bounded_agent`；其他类型拒绝 |
| `executor.ref`, `executor.version` | 受信任注册表中的固定引用；不能是模块路径、下载地址或可执行文本 |
| `allowed_tool_refs` | 模型节点可选择的固定工具子集，仍受运行权限约束 |
| `dependencies` | 固定版本的工具、资料、规则与提示引用；所有实际读取还需记录 |
| `permission_requirements` | 所需动作和资源范围；只是申请，不能自行生成 Grant |
| `effect` | `read` / `project_write` / `external_write`；R0 拒绝第三类用于真实业务 |
| `preconditions`, `postcheck_refs` | 有版本的注册检查和有限条件表达式；不允许任意代码 |
| `limits` | 步数、请求次数、总用量、时限与修复上限；只能收紧平台上限 |
| `idempotency`, `reconcile_ref` | 幂等种类、结果核对执行器和安全重试条件 |
| `error_contract` | 可公开的类型化错误、是否可重试、需要什么介入 |

确定性计算交给工具；需要语言理解的节点通过统一书生适配器执行。一个 ActionSpec 不能声明“我已获准访问所有项目”而获得相应权限。

### 5.3 AppManifest 最小契约

清单至少包含 `schema_version`、`app_id`、`revision`、`origin`（`goal` 或 `task_run`）、`goal_ref`、`input_schema`、`output_schema`、`views`、`workflow`、`action_bindings`、`data_bindings`、`runtime_identity_requirements`、`permission_requirements`、`dependency_lock`、`validation_suite_ref`、`runtime_limits` 和 `data_schema_version`。

`origin=task_run` 时必须关联来源运行，但正式应用不能依赖它的会话上下文或越权材料。`runtime_identity_requirements` 只描述所需身份，不包含平台管理员身份或凭证。

R0 的 `workflow` 为有限有向无环图，允许有类型的条件分支；模型节点内部是受步数与预算限制的调用循环。分支表达式只支持经过实现和测试的操作符，例如 `eq`、`in`、`exists` 及有限逻辑组合，不使用 `eval`。循环、递归调用、动态安装工具和跨应用触发留到后续阶段。

视图只引用注册组件和输出字段。模型不能写 `<script>`、任意 HTML、任意 URL iframe 或动态 JavaScript 进入平台页面。Markdown 经过安全渲染，链接和文件访问经后端权限检查。

### 5.4 清单编译与执行顺序

候选 JSON → 严格解析与类型校验 → 注册引用解析 → 输入输出连通性检查 → 依赖与权限预检 → 预算检查 → 生成不可变执行计划 → 私有预览与验收 → 发布绑定。

采用明确 JSON Schema 子集；禁止重复键、NaN、外部 Schema `$ref`、任意路径与不认识的字段。深度、文件大小、行数和执行规模均有配置上限。所有上限在 F1 配置契约中确定，不能由模型提高。

结构正确不代表业务正确；清单通过 Schema 后仍需独立验收。结构错误只反馈定位信息供有限修复，不先执行“看得懂的部分”。

### 5.5 身份与权限

至少区分创建用户、项目调用用户、应用运行身份、后端服务身份。即使本地体验只有一个实际用户，也要有两个测试主体和两个项目验证隔离，不能仅靠前端隐藏对象。

手动运行有效权限为：当前用户可用权限 ∩ 发布版本声明的能力 ∩ 应用身份获授范围 ∩ 当前资源授权。模型产生的是权限需求，Grant 必须由服务端在用户授权后创建。后续自动任务另用专用身份，不能继承创建者全部权限。

每次读取敏感资源、调用工具或提交副作用前重新检查授权及撤回版本；缓存、旧 checkpoint 和历史审批不能绕过撤回。已发出的远程请求不能被“撤权”追溯撤销，应记录时间边界与无法收回的影响。

### 5.6 必要 API 行为

创建运行返回 `202 + run_id` 的前提是目标、输入快照与队列记录已持久化。轮询/SSE 只读持久事件；浏览器断线不构成取消。

页面和内部 API 都调用同一个动作网关。提交使用幂等请求键；相同键和相同请求返回原运行/结果，相同键但请求指纹不同返回冲突。用户明确发起另一次运行才创建新逻辑操作。

暂停、取消、继续、批准、发布、撤权是独立授权命令。需要旧版本前置条件的命令使用版本比较；错误区分格式错误、权限拒绝、版本冲突、资源不可用及执行结果不明。

### 5.7 统一结果、错误与持久状态

动作返回统一结果封装：`operation_id`、`status`、`data`、`artifact_refs`、`receipt_ref`、`check_results`、`usage_ref`、`error`。`status` 与 Operation 账本映射，不以模型一句“完成”赋值；失败时保留已经产生的可见成果，未知效果必须显式标出。

`error` 至少含 `code`、面向用户的安全信息、是否可安全重试、是否已知发生副作用、需要用户采取的操作。可用错误码包括 `INVALID_INPUT`、`INVALID_MANIFEST`、`UNSUPPORTED_CAPABILITY`、`PERMISSION_DENIED`、`GRANT_REVOKED`、`NEEDS_INPUT`、`RESOURCE_UNAVAILABLE`、`RATE_LIMITED`、`MODEL_OUTPUT_INVALID`、`MODEL_TIMEOUT_OR_TRUNCATED`、`BUDGET_EXHAUSTED`、`VERSION_CONFLICT`、`LOCK_CONFLICT`、`OUTCOME_UNKNOWN` 和 `VERIFICATION_FAILED`。重试标志由执行器按账本和权限决定，不由模型自行设置。

状态也要有类型：输入快照和运行上下文属于 Run；业务记录属于 AppInstance；派发与回执属于 Operation；模型对话只是某步骤的上下文。它们不能共用一段由模型自由改写的“全局记忆”。保存上下文不应暴露凭证或模型私有推理内容。

以下仅为两类契约的关系示意，**不是可以直接执行的完整清单**：

```json
{
  "ActionSpec": {
    "action_id": "action_stable_id_assigned_by_server",
    "revision": 1,
    "executor": {"kind": "registered_tool", "ref": "data.aggregate", "version": "1"},
    "input_schema": {"type": "object", "properties": {"dataset_ref": {"type": "string"}}, "required": ["dataset_ref"], "additionalProperties": false},
    "effect": "read"
  },
  "AppManifest": {
    "app_id": "app_stable_id_assigned_by_server",
    "revision": 1,
    "origin": "goal",
    "action_bindings": [{"binding_id": "aggregate", "action_id": "action_stable_id_assigned_by_server", "revision": 1}],
    "runtime_identity_requirements": {"mode": "user_and_app_intersection"}
  }
}
```

正式 Schema 还必须要求 §5.2—5.3 的其余字段；示意中的 `dataset_ref` 由后端解析为有权限的资源，字符串自身不构成访问权。样例只有 JSON 语法合法性，不代表注册工具或平台已经实现。

## 6. Windows 运行边界

### 6.1 选择一条主验收路径

【设计决定】R0 主路径为 **Windows 11 x64 原生运行**：PowerShell 启动前端构建、API 与独立 Python worker，PostgreSQL 使用 Windows 服务，文件保存在明确的本机数据目录。不要求先安装 WSL2 或 Docker 才能体验声明式应用。

这是待验证目标，不是已完成兼容性声明。目标 OS build、Python、Node、PostgreSQL、PowerShell 及依赖的精确版本在 F1 通过测试后锁定；不写“任何 Windows 都可运行”。PostgreSQL 官方提供 Windows 安装入口。[W2]

### 6.2 各组件在哪里运行

| 组件 | Windows 原生主路径 | 远程依赖与注意事项 |
| --- | --- | --- |
| 前端 | 浏览器中运行；静态资源由本机 API 提供；开发模式可单独运行 Vite | 默认不从第三方加载私有资源 |
| API | 本机 Python 进程，默认仅绑定 `127.0.0.1` | 对外暴露须另配身份、TLS、防火墙与审查 |
| worker | 本机独立 Python 后台进程，数据库领任务 | 不是浏览器线程，也不是一次 HTTP 请求里的临时任务 |
| 数据库 | 本机 PostgreSQL Windows 服务 | API/worker 使用应用角色；迁移角色与运行角色分离 |
| 文件 | 配置的本机数据根目录，按逻辑项目/运行 ID 管理 | 不把仓库内临时文件、系统目录或凭证目录当作应用输入 |
| 书生模型 | 远程官方托管 API | 需要网络和真实账号；批准的内容可能发送到服务端 |
| 生成应用 | 浏览器可信组件 + 本机声明式运行器 | 不需要为每个应用启动新服务器或执行模型代码 |
| 任意生成代码 | R0 不执行 | F4 隔离路线与门槛通过后才可能启用 |

“本地启动”不等于完全离线。没有书生凭证时，可跑标记清楚的工程样例和离线测试；不能把它们作为真实智能体接入证据。

### 6.3 与 WSL2、远程访问严格区分

WSL2 使用 Linux 内核及受管理虚拟机，不是 Windows 原生进程环境。[W1] 将来提供 WSL2 路径时，须分别说明 Linux 中的 API/worker/数据库、Linux 文件路径、Windows 浏览器访问方式，并独立执行验收。

从 Windows 浏览器访问远程服务器，只证明远程部署可访问，不证明项目能在 Windows 本机拉取并启动。远程部署的计算、文件与数据库在服务端，本机是否开机不决定服务端任务是否运行。

本版不把 WSL2 或 Docker 当作已经验证的生成代码安全沙箱；环境隔离能力与安全边界要单独验收。

### 6.4 关闭与断线语义

| 事件 | 预期行为 |
| --- | --- |
| 关闭/刷新网页 | 已持久化任务继续由存活 worker 执行；重开可读取状态 |
| 关闭前端开发服务器 | 前端暂不可访问；worker 是否继续由其独立进程决定 |
| 停止 API | 不接受新请求；已有 worker 可继续已持久化且授权有效的任务；审批交互等待 API 恢复 |
| 正常停止 worker | 停止领新任务，保存进度；未安全完成的动作进入核对状态 |
| 杀死 worker 或电脑休眠 | 处理停止；恢复后通过租约与操作账本核对，不盲目重试 |
| 电脑关机/断电 | 本地 API、worker 和数据库均不能继续执行；远程在途请求可能有未知结果 |
| 关闭启动终端 | 不能默认承诺后台存活；以启动方式和 PID 检查结果为准 |

需要全天候执行时，必须部署在常在线机器或服务上，并配置监控、存储与凭证。R0 不承诺自动安装 Windows 服务、开机自启或关机后任务继续运行。

## 7. 书生模型：真实链路与托管约束

### 7.1 已核查事实与实施决定

官方 Chat Completions 文档注明：默认每用户每分钟 30 次请求；工具调用不支持流式；模型 120 秒未完成输出时会被打断并返回当前结果；兼容 OpenAI SDK 的部分方法，并非全部接口。[A1]

官方模型列表明确 `intern-s2` 为调用 ID，并公告 `intern-s2-preview-397b` 将于 **2026-10-31** 下线。[A2] 因此首选验证 `intern-s2`，不依赖将下线的 Preview，也不把 `intern-latest` 当作固定版本。具体账号是否可调用、额度与其他限制仍为【待实测】。

官方页面的简略参数列表和详细参数表并不完全一致。因此采用能力白名单与账号探针，不能机械地假定严格 JSON、所有参数、所有 SDK 方法或本地部署参数均兼容。深度思考模式按官方推荐保持默认，不用强行关闭来伪造更低时延。[A1][A2]

### 7.2 真实链路职责

书生模型负责目标理解、计划形成、工具选择、候选清单、错误反馈后的修订。注册工具负责解析、计算、读写和验证；后端负责授权与事务。开发时使用的 Codex/GPT 不属于产品运行模型，也不得静默参与正式应用推理。

每次真实运行保存请求模型 ID、返回模型字段、模型列表快照（含可获得的 `ref_model`）、时间、适配器版本、调用参数摘要、工具轨迹、失败和用量。服务端未提供底层权重版本时写“未知”，不能把 API 名称固定等同于权重永远不变。

### 7.3 统一请求调度

所有创作、应用、验证、修复和能力探针共用限流器。限流键对应**上游账号配额主体**，而不是给每个 Sim2Act 用户或每个 worker 都分配完整 30 RPM；同一账号多个密钥也不能默认额度相互独立。

F1 用数据库中的配额主体与请求预约记录实现跨进程协调。未核实更高额度前，不超过已知默认限制；账号还有 TPM、并发或月额度时一并配置。上游账号被其他程序共用可能占用额度，需保留 429 等反馈和退避机制，不声称本地限流可以防止一切上游拒绝。

API 请求使用 `stream=false` 完成工具循环；前端可接收平台进度事件，但这不是上游流式 tool call。SDK 自带重试应关闭或纳入统一尝试计数，禁止隐藏的多层重试。

### 7.4 截断、结构与进度处理

每次模型请求前保存步骤及预算状态。收到返回后，校验 HTTP/业务错误、结束原因、完整 JSON、工具名称、参数类型与权限，再分发工具。120 秒是服务端输出限制，不是任务总时限；调大客户端超时不能绕开它。[A1]

输出截断、不完整工具参数或状态不明时，不执行半截动作。缩小上下文、拆分可恢复步骤或有限重试；不能直接拼接残缺 JSON 后当作有效授权。若服务端没有明确截断标志，结构异常或结束原因不明按失败处理，不能猜测成功。

模型请求耗时较长时，worker 心跳必须独立维护。断线重试模型可能产生重复计费，记录每次尝试；工具副作用则另走操作账本，不跟随模型重试而重复执行。

### 7.5 能力与用量报告

`capability-report` 应含：模型可见性、一次真实工具调用及结果回填、支持参数、非流式行为、结构错误样例、错误处理和已知额度。人为注入 429/截断属于工程故障测试，不得标为真实服务端已触发验证；不为探测而故意压满公共接口。

限制配置包括模型轮数、工具次数、有限修复、单次输出、总 Token/调用量和运行时限。具体预算由用户及账号条件确认；未设有效上限不能无限执行。

用量缺失时保留 `usage_status=unknown/partial`，记录已知调用和保守占额，不能填零。价格未确认时只报告 Token、次数和时间，不凭空折算费用或承诺免费。

## 8. 持久任务、操作账本与权限语义

### 8.1 持久化与 worker 租约

接受任务后，在数据库事务中保存 Run、输入快照和队列行，再返回接受回执。worker 用短事务领取任务、分配租约和单调递增 fencing token；耗时模型调用不持有数据库长锁。

可使用 PostgreSQL 队列表与 `FOR UPDATE SKIP LOCKED` 领取工作；官方将该机制列为队列式多消费者可用的场景，并不意味着普通业务查询可忽略一致性。[D1]

每一步的结果和下一步意图持久化。租约过期后先进入核对；旧 worker 的 token 不再能提交新状态或本地写入。旧 worker 已发出的第三方请求仍可能生效，因此新 worker 不得仅凭“租约过期”重复派发该逻辑操作。

LangGraph checkpoint 可保存编排状态，但恢复可能重入节点，不保证外部动作只执行一次。[L1] 权限、幂等、回执与未知结果是本平台独立的执行规则。

### 8.2 运行状态

Run 状态固定为：`QUEUED`、`RUNNING`、`WAITING_INPUT`、`WAITING_APPROVAL`、`WAITING_RESOURCE`、`PAUSE_REQUESTED`、`PAUSED`、`CANCEL_REQUESTED`、`RECONCILING`、`SUCCEEDED`、`PARTIAL`、`FAILED`、`CANCELLED`。

| 事件 | 状态变化与执行语义 |
| --- | --- |
| 领取已排队任务 | `QUEUED → RUNNING`；重新检查身份和预算 |
| 需要资料/批准/连接或额度 | 进入对应等待状态，保存原因；不占空转循环 |
| 用户暂停 | 记录 `PAUSE_REQUESTED`；停止派发新动作，在可确认边界进入 `PAUSED` |
| 用户取消 | 记录 `CANCEL_REQUESTED`；不派发新动作，已在途动作核对后进入 `CANCELLED` |
| worker 失联 | 写 `WORKER_LOST` 事件并进入 `RECONCILING`；核对后重排安全步骤或等待介入 |
| 授权撤回 | 后续受影响动作拒绝，进入 `WAITING_RESOURCE` 并记录 `GRANT_REVOKED`；已在途效果另核对 |
| 继续/恢复 | 用户或策略明确继续后重新检查发布、输入、Grant、预算和未决 Operation |
| 完成 | 全部必需结果与验收通过才 `SUCCEEDED`；部分交付明确 `PARTIAL` |

暂停/取消不是强行中止已发生的外部效果。仍有结果不明操作时保持 `RECONCILING` 并保留取消意图，不展示“已取消且没有影响”。`CANCELLED` 也必须附带此前已经发生的效果列表。

### 8.3 Operation 状态与幂等

Operation 状态固定为：`PREPARED`、`DISPATCHED`、`RECEIPT_KNOWN`、`VERIFIED`、`FAILED_SAFE`、`OUTCOME_UNKNOWN`、`EFFECT_KNOWN_INVALID`。

先持久化逻辑操作 ID 与请求指纹，检查最新授权和 fencing token，再派发。重试相同意图使用相同操作 ID；新一轮显式运行使用新 ID。副作用后收到回执，保存真实对象标识，再执行回读或后置检查。

| 动作种类 | 幂等与核对策略 |
| --- | --- |
| 纯读取/确定性计算 | 在预算与授权内重试，记录输入版本；新返回仍需校验 |
| 本地记录写入 | 唯一操作约束；业务变更与操作回执在同一数据库事务中提交 |
| 文件生成 | 固定逻辑成果 ID、临时写入后原子落位、内容指纹与核对；文件/数据库非同一事务的窗口显式处理 |
| 支持幂等键的外部接口 | 使用接口承诺的键及有效期，读回远程结果；不能超过对方承诺范围 |
| 无幂等保证的外部接口 | 先按回执/业务对象核对；无法证明失败时 `OUTCOME_UNKNOWN`，不自动重发 |

“没有收到成功响应”不等于“没有执行”。回读发现效果已发生但不符合要求时进入 `EFFECT_KNOWN_INVALID`，不能重复创建来碰运气。补偿必须是另一个带权限和前提的操作，不自动声称撤销成功。

R0 的真实副作用仅为项目/应用实例内本地写入。外部故障行为通过受控测试适配器验证；将来新增连接器必须另测真实接口的幂等与核对能力。

### 8.4 审批与撤权

Approval 绑定请求/变更指纹、应用发布、资源范围、数据前置版本、调用身份、有效期和授权修订号。方案或相关前置条件变化导致批准过期，必须重新预检。

应用权限不是一份一次性快照。撤权后不得通过缓存读取、旧运行或另一个入口继续访问；输出对用户可见前也要重新检查访问权。已经发送到远端的资料无法靠本地撤权收回，此限制须明确显示。

本地写入的授权最终检查与提交应有清楚的事务边界。远程发送与撤权存在不可原子化窗口，记录派发时刻和在途状态，不承诺瞬时撤销已发请求。

## 9. 交付图与增量修改

### 9.1 节点与依赖

节点类型：`GOAL`、`REQUIREMENT`、`SOURCE`、`ARTIFACT`、`ACTION`、`VIEW`、`CHECK`、`MANIFEST`、`RELEASE`。每个节点具有服务端稳定 ID、不可变 revision、内容指纹、所属项目、状态和人工锁定信息。

边方向统一为**上游 → 受影响的下游**。

| 边类型 | 含义与处理 |
| --- | --- |
| `DATA` | 数据或字段依赖；输入变化使相关结果与检查失效 |
| `RULE` | 目标、规则、配置影响动作或成果语义 |
| `PRESENTATION` | 展示依赖；已证实仅展示变化时可保留计算结果 |
| `SEMANTIC` | 语言含义关联；可能不完整，采用保守重验 |
| `VERIFIED_BY` | 对象指向检查；对象版本变化后旧检查不再证明新版 |
| `PACKAGED_IN` | 组成部分指向清单/发布；发布证据必须绑定精确组成 |

每条边记录来源：编译器声明、运行实际读取、人工确认或模型候选。模型候选不能被当作已穷尽的依赖。静态类型检查、实际读取记录和人工证据共同补充图。

### 9.2 指纹与确定性边界

对象指纹由规范化定义、相关上游修订、工具版本、Schema、提示与验收版本共同形成。运行再记录输入快照和实际读取范围。ID 表示“同一个逻辑对象”，指纹表示“是否同一版本”；改内容不重新发明所有对象 ID。

资源列表查询也属于依赖：新文件加入或记录集合变化会改变集合指纹，不能只跟踪已经读到的文件。动态访问无法界定时，登记对应资源集合或项目范围的“不确定依赖”。

数据、权限和发布状态不能只靠内容缓存判断。缓存复用也重新授权，且保留缓存来源和版本。不能因文本相似就认定语义未变化。

### 9.3 修改执行规则

1. 保存变更请求和基线版本；标出明确目标与可选范围。
2. 按类型化边和实际读取范围求候选影响集，分别标记“确定影响”和“影响不确定”。
3. 失效传播到相关成果、动作、视图、检查和发布候选，不抹掉历史成功记录。
4. 对确定无关对象保留 ID、内容、人工改动和版本；对受影响对象形成草案补丁。
5. 有未知依赖时扩大重验范围到关联应用，必要时整个项目；这不等于立即重写整个项目。
6. 若影响集碰到人工锁定对象，返回 `LOCK_CONFLICT`，保留原内容；等待解锁、明确改范围或放弃变更。
7. 运行受影响检查和必要的全局不变量；未决冲突不得发布为“已验证”。
8. 发布前比较源版本与前置数据，冲突则重做预检；通过后生成新 Release。

“最小修改”是优化目标，不是可靠性保证。与安全、正确性冲突时优先扩大检查范围，不能为了显示节省成本而漏测。

### 9.4 衡量漏更新与误修改

由独立答案定义应修改集与应保持集；不能让生成器自行把全部对象都算作受影响来规避误改统计。

至少报告：应更新对象中未正确更新的数量与比例、应保持对象中被无必要修改的数量与比例、相关检查失效是否传播、锁定内容保留、人工修复量、重验范围和总用量。样本分母为零时记为不适用，不能填百分百。

若实现只能全量重做，应如实标注增量能力未通过，不能以“更保守”为由把任意无关改写也算正确。

## 10. 发布、业务数据与代码隔离

### 10.1 发布不可覆盖业务数据

AppRelease 是不可变规格；AppInstance 保存独立业务数据与运行记录。新版本产生新 Release，不删除旧实例数据。预览使用独立测试命名空间，不能调用生产写入目标。

发布绑定经过验证的 Schema、动作、工具、提示、模型配置与检查版本。更新发布指针采用版本比较；运行开始时固定使用某个 Release，不能执行一半切到新版，但每个动作继续检查动态权限。

R0 只支持经过兼容性验证的升级。破坏性字段删除、类型变化或不可兼容的数据迁移直接阻止发布。回退 Release 前也检查当前数据是否兼容。

**发布回退 ≠ 数据回退 ≠ 外部动作撤销。** 数据备份、迁移和补偿是独立操作与独立证据。

### 10.2 R0 禁止生成代码执行

模型输出的 Python、JavaScript、Shell、SQL、动态模板表达式以及依赖安装命令均不得执行。它们至多作为未执行文本成果保存，并明确状态。

可信工具可以在独立本地进程运行以限制资源和便于取消，但这只是故障隔离，不自动构成对恶意代码的安全沙箱。工具从项目内注册表加载，模型不能注册新执行器。

文件使用逻辑资源 ID；服务器限制根目录、大小和类型，并测试 Windows 的盘符、UNC、备用数据流、路径穿越和重解析点等越界情况。应用只能取得获授权的文件，不接受凭证目录或任意本机路径。

### 10.3 后续代码隔离选型门

隔离路线当前标记【待选型，未验证】，F4 再决策。候选包括单独执行虚拟机/经强化的远程运行服务，或满足限制条件的容器化执行器；普通子进程或仅安装 WSL2 不足以直接开放任意生成代码。

必须验证：独立最小身份、按次工作目录、只读基础环境、CPU/内存/进程/磁盘/时间上限、默认禁网及显式目的地放行、依赖来源锁定、文件输入输出检查、销毁与清理、审计、取消和异常回收。

生成环境不能获得宿主目录、全量环境变量、数据库管理员、平台密钥、云元数据凭证、Docker socket 或任何容器/主机控制权。凭证通过有范围的工具代理调用，不直接注入任意生成代码。

验证需覆盖读其他项目、网络越界、资源耗尽、逃逸尝试、秘密外传、残留数据和失联清理。门槛不通过则保持功能关闭；“已经放进容器”不能代替隔离验收。

## 11. 验收与对照原则

配套计划定义固定测试 AT-01—AT-28 及增强测试 EX-01—EX-06。F1 建立测试资产和预期输出，F2 用于两条生成路径及局部修改，F3 完成首版验证，不推迟到 F7。

每例至少含目标、输入、权限、起始状态、允许的人工交互、应有成果/状态、不允许的副作用、独立检查、预算配置和重置步骤。验收定义在生成前冻结；模型可以建议新检查，但无权删除或降低既定标准。

确定性结果采用独立计算或人工小样例；语义成果采用来源核对和固定人工量表，自动引用定位只证明来源存在，不证明推断正确。真实任务与故障注入分开报告，回放与实时模型执行分开报告。

对照至少包括同书生模型、同工具/渲染组件、同权限保护和合理预算的通用智能体；增量实验以相同起始应用比较受控修改与全量重建。安全保护不作为可关闭的消融。任务应用化另比较对新输入重复对话与复用应用的总成本，包含第一次构建和验证成本。

记录完成率、正确性、人工介入、主动用时、端到端耗时、模型/工具调用、Token、验证与修复开销及未知用量。部分完成、暂停、拒绝、失败和预算耗尽均保留，不能只统计成功例。工程门槛是固定用例通过，不是声称现实环境零风险或某个获奖概率。
